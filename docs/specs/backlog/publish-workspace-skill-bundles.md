# Backlog Spec: Publish Workspace Skill Bundles

## Status

State: `backlog`

Rationale: The namespace-manifest extension and validation contract are
specified, but no schema-2 Workspace release has been generated, reviewed, or
published.

## Companion Specifications

This specification is the Registry distribution part of one coordinated
change:

- Workspace: `All Workspace Skills Bundle`
- SKM: `Install Workspace Skill Bundles`

The three specifications must keep the bundle identifier, manifest fields,
version rules, validation behavior, and rollout order aligned.

## Problem

The Registry publishes nineteen immutable packages in the `workspace`
namespace, and its schema-1 namespace manifest binds those packages to one
Workspace toolkit release and source revision. It does not publish named bundle
membership. SKM therefore has no registry-owned, reviewable way to distinguish
the complete current Workspace skill set from unrelated directories, stale
packages, or a manually maintained client list.

Registry must distribute canonical bundle metadata without becoming a second
editor of Workspace product definitions or weakening exact-version
immutability.

## Goals

- Publish named, version-bound Workspace skill bundles in the Workspace
  namespace manifest.
- Support the canonical `all-workspace-skills` bundle generated by Workspace.
- Guarantee that this special bundle contains the complete package set exactly
  once.
- Validate bundle identity, membership, ordering, versions, provenance, and
  compatibility alongside the existing package contract.
- Preserve exact-version immutability and additive publication.
- Give SKM one trusted manifest from which it can plan a project-local bulk
  addition.

## Non-Goals

- Authoring or hand-editing Workspace bundle membership in Registry.
- Discovering bundle members by scanning package directories.
- Publishing Workspace agent profiles.
- Defining SKM CLI, config, link, or transaction behavior.
- Replacing package dependency metadata with bundles.
- Deleting or rewriting schema-1 manifests from historical revisions.
- Introducing ranges for package versions or cross-registry dependencies.
- Allowing a bundle publication to bypass normal Registry review and CI.

## Namespace Manifest Schema 2

The current `skills/workspace/manifest.yaml` contract advances from schema 1 to
schema 2. Schema 2 preserves every current release field and adds a `bundles`
mapping:

```yaml
schema_version: 2
namespace: workspace
toolkit_version: "<exact-semver>"
source_repository: "https://github.com/skills-yaml/workspace.git"
source_revision: "<full-commit>"
workspace_docs_compatibility: "<range>"
minimum_skm_version: "<exact-semver>"
skm_adapter_compatibility: "<range>"
packages:
  <skill-id>: "<exact-semver>"
bundles:
  all-workspace-skills:
    packages:
      - <skill-id>
```

Schema requirements:

- Bundle identifiers follow the same safe lowercase hyphen-case constraints as
  package identifiers.
- `bundles` is non-empty for the schema-2 Workspace release.
- A bundle contains a non-empty `packages` sequence of unique identifiers.
- Every member is a key in the same manifest's `packages` mapping and therefore
  resolves to one exact semantic version in the selected release.
- Bundle and member ordering is deterministic.
- The `all-workspace-skills` member set equals the complete `packages` key set;
  no published package may be omitted and no additional member may appear.
- Profiles and arbitrary filesystem paths are not valid bundle members.
- Unknown fields fail closed unless a later versioned schema explicitly
  permits them.

The manifest is generated from the canonical Workspace toolkit manifest at the
declared full source revision. Registry reviewers and validators verify it;
they do not maintain a divergent bundle list.

## Validation Design

Extend Registry validation to:

1. Parse schema 1 for the existing package-only contract and schema 2 for the
   new bundle contract.
2. Reject unsupported schema versions before traversing package paths.
3. Validate bundle identifiers and sequences before using identifiers in path
   construction or diagnostics.
4. Require each member to resolve through the manifest's exact `packages`
   mapping and the existing immutable package directory and alias checks.
5. Enforce the complete-set invariant for `all-workspace-skills`.
6. Retain shared release-field agreement between the namespace manifest and
   every package's metadata.
7. Compare exact version trees with the production base and reject deletion or
   content/type mutation as today.
8. Validate generated-root/current copies and aliases without following an
   escaping symlink.

Representative negative fixtures cover missing, duplicate, unknown, unsafe,
unsorted, and non-string members; missing or extra all-bundle members; invalid
identifiers; malformed mappings; unsupported schemas; provenance mismatch;
and exact-version modification.

## Publication Behavior

- Workspace's revision-verified packager emits the complete schema-2 namespace
  release.
- Workspace's staging helper copies that manifest and all new exact package
  versions into a temporary Registry transaction.
- Registry validation runs before the release branch is pushed and again in
  Registry CI.
- Publication occurs only through a reviewed Registry pull request.
- Existing exact versions and historical schema-1 Git revisions remain
  unchanged.
- Rerunning the same generated release is idempotent; a semantic no-op must not
  create a new publication commit.

The current shared source-revision contract means a new Workspace source
revision requires newly versioned generated packages rather than modifying the
currently published versions, even when a skill body did not otherwise change.

## Compatibility and Migration

- Current Registry consumers may continue resolving individual Workspace
  packages and their exact dependencies.
- The current schema-1 manifest remains valid at its published Git revision.
- The Workspace namespace moves to schema 2 only with a package set generated
  for the same source revision and with a minimum SKM version that supports
  bundle consumption.
- Registry's parser and tests must distinguish historical schema-1 validation
  from current schema-2 requirements; they must not rewrite history.
- A schema-2 release without `all-workspace-skills` is invalid for this
  namespace release.

## Security and Reliability

- Treat generated manifests and package trees as untrusted input.
- Validate names and versions before filesystem access.
- Reject all symlinks except the established contained version aliases.
- Verify canonical source repository, full source revision, source paths,
  integrity values, and shared metadata agreement.
- Keep package dependency resolution exact and within the same namespace.
- Preserve comparison-to-production immutability checks.
- Keep Registry publication credentials outside this repository and rely on
  the existing scoped, review-only Workspace publication workflow.
- Do not expose tokens, credentials, runner paths, or other sensitive values in
  manifests, test fixtures, CI logs, or documentation.

## Acceptance Criteria

1. The current Workspace namespace manifest uses schema 2 and includes a
   deterministic `bundles` mapping generated from a released Workspace source
   revision.
2. `all-workspace-skills` lists every manifest package exactly once and no
   profile or unknown identifier.
3. Every bundle member resolves to the exact package version declared in the
   same manifest.
4. Validation accepts the intended schema-2 release and preserves validation
   of the historical schema-1 contract.
5. Validation rejects malformed identifiers or structures, duplicates,
   unknown members, incomplete or oversized all-bundles, unsafe paths,
   provenance drift, and modified exact versions.
6. Publication preserves all historical exact versions and stages the manifest
   and packages transactionally.
7. A repeated publication of identical generated content is a no-op.
8. Registry documentation explains schema 2, bundle semantics, the special
   complete-set invariant, and the separation from dependency metadata.
9. A compatible SKM build can preview and apply the published bundle, pass
   `skm check`, and converge without changes on a second apply.
10. Workspace, Registry, and SKM agree on the bundle identifier, membership,
    source revision, exact versions, and compatibility metadata.

## Implementation Plan

1. Freeze schema 2 and the special bundle invariant with the Workspace and SKM
   companion specifications.
2. Add schema-2 parser and validator coverage while retaining schema-1 fixtures.
3. Accept a revision-verified generated release from Workspace and verify its
   manifest-to-package agreement.
4. Stage new exact versions additively and validate immutability against
   Registry `main`.
5. Update Registry documentation and inventory.
6. Run full Registry gates and a security review of untrusted manifest parsing,
   paths, symlinks, provenance, dependencies, and immutable releases.
7. Merge through Registry review only after Workspace release evidence exists,
   then execute the SKM end-to-end consumer test.

## Rollout and Rollback

Workspace releases the canonical bundle first. Its existing publication
workflow then opens a revision-specific Registry pull request containing the
schema-2 manifest and newly versioned package set. Registry merges only after
local and CI validation. SKM releases the consumer command last, followed by a
fresh-project end-to-end check.

Before Registry merge, close the publication pull request and delete its
release branch to roll back. After merge, never rewrite or delete published
exact versions; publish corrected package versions or restore aliases to a
known-good compatible release through a new reviewed change. Historical Git
revisions retain the schema-1 manifest for older consumers.

## Risks and Mitigations

- **Bundle/package drift:** enforce exact set equality in Workspace generation
  and Registry validation.
- **Mutable meaning of “all”:** bind membership to exact package versions,
  toolkit version, and immutable source revision.
- **Supply-chain input abuse:** fail closed on schema, identifier, path,
  symlink, provenance, integrity, and dependency validation.
- **Large coordinated release:** preserve additive publication, deterministic
  generation, transactional staging, and no-op reruns.
- **Consumer skew:** declare minimum SKM compatibility and release SKM only
  after the Registry artifact is available.

## Alternatives Considered

- **Infer all packages from directories:** rejected because stale or unrelated
  directories are not a release contract.
- **Maintain a Registry-only list:** rejected because Workspace owns the
  canonical product inventory.
- **Publish a meta-package depending on every skill:** rejected because it
  creates an extra installed skill and conflates dependency and bundle
  semantics.
- **Allow floating package aliases in bundles:** rejected because reproducible
  project configuration requires exact versions.
